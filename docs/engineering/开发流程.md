# Folio 工程规范与双人开发流程

两人按可验收的功能动态领卡。前端与本机后端约定接口后并行开发，最终用同一 APK、同一份本机数据联合验收。项目维护者审核并合并所有 PR。

本文约定安卓工程建立后的工作方式。当前仓库处于设计阶段，Gradle 命令、自动化测试和 CI 须在工程起步 PR 中首次跑通。产品范围、迭代顺序与设备要求见[版本规划](../requirements/版本规划与审核事项.md)，共同交付要求见[协作分工](../requirements/协作分工.md)。

## 一、开工前，从需求得到一张可执行的卡

1. 从[需求总索引](../Folio-需求与设计文档-v0.1.md)找到本轮涉及的需求编号，读对应正文和[本轮范围](../requirements/版本规划与审核事项.md#首版迭代安排已确认)。例如第一批实现正文搜索，组合筛选留到相应轮次。
2. 涉及保存、媒体或查找时，核对[已确认的保存关系](../design/首版原型与关键数据设计.md#已确认的保存关系)，再查看相关代码、测试与已有接口。原型中的示例用于核对行为，表结构以实际工程为准。不同材料对用户行为有冲突时，带着具体例子核对[待确认问题](../requirements/待确认问题.md)，其余独立任务可以继续。
3. 每张卡写四项：**需求依据、本次范围、接口与依赖、验收例子**。范围写到用户能做什么，验收例子给出初始数据、操作和可观察的结果。卡片或 PR 描述均可承载这些信息；同一任务只维护一份。
4. 领卡时标为「进行中」，使用同一任务标识关联分支、commit 和 PR。人员贡献查 commit 与 PR，卡片省去责任人字段。提交 PR 等待审核时，可以领取下一张依赖已就绪的卡；原 PR 的反馈仍由作者跟进。

## 二、前端和本机后端的边界

首轮使用 Kotlin、Compose 和 Room／SQLite。前后端在一个 `:app` 模块内按职责组织，通过进程内 Kotlin 接口协作，基础操作在手机本地离线完成。

| 部分 | 负责 | 边界 |
|---|---|---|
| 前端（Compose、ViewModel） | 输入、导航、编辑位置、加载、空结果、失败和成功反馈 | 页面发出动作并展示状态。ViewModel 调用业务接口，收到持久化成功结果后再显示「已保存」。 |
| 业务接口 | 草稿、完成、查找和媒体等操作的输入、输出与失败行为 | 使用业务 ID、内容和可观察结果。需要持续刷新时使用 Flow。变更接口时同步核对调用方和已有数据。 |
| 本机后端 | Room 查询、提交事务、媒体原件、回收站、迁移 | 集中执行“只检索有效正式记录”等规则。DAO、Entity 和持久文件路径由实现管理；搜索、列表和详情引用同一份记录。 |

**首批接口约定**（名称可随代码约定，行为须一致）：

| 操作 | 输入 → 成功结果 | 失败或边界行为 |
|---|---|---|
| 保存／续写草稿 | 当前文字及编辑位置 → 成功落盘的草稿 ID；按该 ID 重开 → 上次成功保存的内容和位置 | 空编辑退出不新建草稿；写入失败如实提示，可重试。中断恢复以成功落盘的内容为准。 |
| 完成草稿 | 草稿 ID 与最终编辑状态 → 稳定的正式记录 ID | 先确保最后一次输入参与本次提交；正式内容写入与本次草稿移除同属一个 Room 事务。失败保留草稿和已有正式版本，重试成功只产生一份结果。 |
| 搜索正式记录 | 中文关键词 → 记录 ID 和预览，按 ID 打开详情 | 未完成修改仍按上次完成的正文匹配。新建草稿和回收站记录不出现在结果中。读取错误与零条匹配分别反馈。 |

只实现本卡用到的接口和错误处理。优先复用已有组件和查询，把同一条业务规则放在一处。有真实的第二个用途或测得的问题时，再评估抽象、拆模块或优化。

## 三、首批任务与合并顺序

下表可直接作为首批卡片。任务标识用于引用示例，实际领卡顺序取决于进度。[文字与保存需求](../requirements/A-记录与保存.md) · [浏览与找回需求](../requirements/B-整理关联与查找.md#b5-浏览与找回)

| 卡／需求 | 本次范围 | 接口与依赖 | 验收例子 |
|---|---|---|---|
| T1　离线文字与完成（R002、R006–R009） | 从「随手记」写字，自动存草稿，重开续写，完成后可查看 | 提供草稿读写、提交和正式记录 ID。先在本地持久库验收 | 写一个字后重开仍可续写。模拟完成事务失败，草稿仍在；重试后只生成一条正式记录。 |
| T2　草稿入口与正式搜索（R008、R023、R024） | 在「记录」选择草稿续写，按正文搜正式记录，打开详情并返回原位置 | 与 T1 约好草稿 ID 和正式记录 ID。先用固定样本做入口、查询与详情，再接实际保存结果 | 正式、草稿、回收站各有一条含“青瓦”的数据，只搜到正式的那条。只有一份草稿直接续写，多份按最近编辑顺序选择。 |
| T3　两端联调（同上） | 在同一安装包确认从起草到找回的整条路径 | T1、T2 可独立验收后共测，结果附在接通两端的 PR | 按下一节复现，记录设备、提交号和实际结果。 |

1. **起步。** 工程起步 PR 提供可安装的最小 `:app`、Wrapper、本地与 CI 共用的构建入口，以及首批要共享的接口。运行条件（JDK、Android SDK 和模拟器）随工程配置记录；CI 使用相同版本。
2. **并行。** 各用自己的 GitHub 账号和功能分支，从最新 `main` 开始。小批 commit，每批围绕一个可复核的改动。可由 AI 按卡实现，提交者阅读差异、运行相关检查并确认验收结果。
3. **合并。** 实际示例可先合 T1，再让 T2 同步最新 `main`，接入真实 Room 并完成 T3。PR 给出任务与需求引用、行为变化、验证结果和未验证项。涉及共享接口或表结构时写明对另一张卡和旧数据的影响。
4. **审核。** 维护者检查行为是否符合本批范围、验收例子能否复现、CI 是否通过。维护者自己发起的 PR 由另一人交叉复核，维护者作最终合并决定。

## 四、联合验收与首轮后续卡

**文字闭环。** 在 Android 10 或以上设备使用空测试库，开启飞行模式，全程无需登录。

1. 从「随手记」输入“青瓦桥初雪”，确认草稿落盘，暂时离开编辑，在「搜索全部记录」查“青瓦桥”，预期 0 条。
2. 强行停止应用，保留应用数据。重新启动，从「记录 → 继续草稿」打开，核对原文和续写位置。
3. 追加“，河边见”并点「完成」。预期回到「随手记」，通过「已保存 · 查看」打开完整正文。
4. 再搜“青瓦桥”，预期 1 条。搜索与保存反馈指向同一记录 ID，草稿入口已移除本次草稿。

**照片。** 拍照／系统选图与原图保存、按顺序预览可分别领卡。先把原件写入应用持久目录并确认可读，再保存草稿引用。联调检验移除相册来源后仍能重新打开原图，保存失败时保留此前成功的内容，拒绝相机权限后仍能写文字。[照片记录](../requirements/A-记录与保存.md#r003-照片记录)

**删除与恢复。** 可先用文字打通删除、立即撤销和回收站，再验“正式旧图＋草稿新图”。删除后两者从普通入口隐藏；回收站只读展示正式内容并提示有草稿；恢复后正式记录可查看、草稿可续写。仍被正式记录、草稿、回收站或可撤销操作引用的原图须保留。[删除恢复规则](../requirements/H-隐私与数据保护.md#删除恢复的共同规则)

首轮出包前，按版本规划补验已有记录的编辑与放弃、文字与照片的插入／移动／移除与撤销、精确或留空的事件时间、自动记录时间和双时间浏览。视觉风格单独评审。[首轮交付范围](../requirements/版本规划与审核事项.md#首版迭代安排已确认)

## 五、构建、验证与 CI

从仓库根目录使用 Wrapper。以下为约定的 Windows 命令；Linux CI 使用 `./gradlew` 和相同的任务名。

| 用途 | 命令／操作 | 通过依据 |
|---|---|---|
| 日常构建与快速测试 | `.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug` | 测试通过，生成可安装的调试 APK。 |
| 设备集成测试 | 先启动模拟器或连接测试设备，再执行 `.\gradlew.bat :app:connectedDebugAndroidTest` | 真实 Room 和涉及 Android 平台的关键路径通过。 |
| 每轮交付 | 在受控签名环境执行 `.\gradlew.bat :app:assembleRelease` | 验签并安装该 APK，按本轮范围验收。签名密钥和密码由发布环境提供。 |

**选择测试看风险。** 将断言放在能够捕获错误的最低成本层。查询排除草稿和回收站，用一个真实 Room 用例覆盖；页面只核对打开正确详情和返回位置。验证落盘可关闭并重开数据库；进程被终止后的恢复用候选 APK 实测。普通文案、布局改动做构建和针对性页面检查即可。修复缺陷时优先保留能复现该缺陷的最小回归；事务失败、照片保存中断、旧库迁移等可能造成数据损失的路径值得专测。

**CI 触发与失败处理。** 面向 `main` 的 PR 每次更新都自动构建并执行快速测试；改动涉及数据库、媒体、迁移或跨模块行为时，加跑对应设备测试。每次合入 `main` 后再次构建并执行核心集成回归。保留测试报告、失败任务日志和调试 APK。PR 作者查看首个失败任务，用同一命令复现、修复并推送复测；`main` 失败时由最近合入相关改动的作者牵头，恢复通过后再交付。

**两项按需验证的实践：**

- **变异测试**用于检查现有测试的辨错能力。例如临时变异查询谓词，使回收站记录混入结果，再运行既有查询测试。若变异存活，先确认它确实改变产品行为，再用一个针对性样本补缺口。适合在关键规则稳定后局部运行，不设全仓分数门槛。
- **形式化验证**用于难以靠几个例子审清的状态组合。若照片引用清理变得复杂，可将替换、放弃、完成、删除、恢复和清理建成有限状态模型，用模型检查器搜索违反“有有效引用的原图仍存在”的操作序列。记录模型边界，发现反例后用该序列检查实现。实际文件读写仍在设备上验证。

## 六、每轮 APK 交付

从已验收的 `main` 提交生成签名 APK，附提交号、版本、变更说明、实测设备与结果、未验证项。首个可用版本验证全新安装；有上一版时，用相同应用 ID、相同签名和更高版本号覆盖安装，核对旧记录、草稿及媒体，涉及数据库变更时验证对应迁移。每轮按新增能力覆盖离线、无 Google Play 服务、相关权限被拒和恢复路径。[设备兼容与交付](../requirements/版本规划与审核事项.md#设备兼容与交付已确认)
