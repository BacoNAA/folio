# Folio 工程规范与双人开发流程

两人按可验收的功能动态领卡。前端与本机后端约定接口后并行开发，最终用同一 APK、同一份本机数据联合验收。一人提交 PR，另一人审核，通过后可直接合并。组合查找的最新实现和验收结果见[全局地点筛选与时间匹配说明](#搜索专项全局地点筛选与时间匹配说明)。

工程起步已提供安卓应用、Gradle Wrapper、单元与设备测试及基础 CI。构建和安装入口见[项目说明](../../README.md#构建和试用调试版)。产品范围、迭代顺序与设备要求见[版本规划](../requirements/版本规划与审核事项.md)，共同交付要求见[协作分工](../requirements/协作分工.md)。

### 第二版 D01 首版覆盖到 Room v22

2026-11-24，`codex/reading-size` 在 Android 10（API 29，默认 x86_64 镜像）用首版 `609908a` 的调试包制备「秋游／明天带伞／旧车票」。目标调试包沿用 PR #38 的构建，其源码与 `main@43334b5` 一致。两包均为 `0.1-dev`（versionCode 1）。保留数据和首版测试 APK，用 `adb install -r` 覆盖后直接从 v17 升到 v22。[任务卡与复跑步骤](../requirements/第二版/升级备份与恢复.md#制备一份可重复使用的首版样本)

- **正常覆盖**　「秋游」的记录 ID、星标、首次记录时间和修改时间均保留，原图和录音的 SHA-256 与首版一致。从搜索打开详情可放大原图、试听至结束。「补记山路」只在编辑草稿可见，「明天带伞」仍可续写。回收站恢复「旧车票」后才可继续编辑「票面铅笔字」。
- **失败后重试**　在另一份相同的首版样本中阻止 Room 登记新结构。「记录」显示读取失败，强停重开仍有重试入口。此时数据库仍是 v17，正式内容表没有残留视频或网址字段。解除故障后在原页点「重试」即可读回两份活动草稿，数据库升至 v22。再次从页面核对了搜索、照片、试听、回收站恢复和续写。[验收用例](../../qa/d01/androidTest/D01UpgradeProbe.kt)

本轮复用两个应用 APK，离线构建首版专用测试 APK 用时 1 分 39 秒。正常覆盖的页面验收用时 9.8 秒，故障后的首次打开、冷启动重试和页面复验三项均通过。实测范围是同签名调试包，正式签名包覆盖随 D04 验收。

## 二、前端和本机后端的边界

首轮使用 Kotlin、Compose 和 Room／SQLite。前后端在一个 `:app` 模块内按职责组织，通过进程内 Kotlin 接口协作，基础操作在手机本地离线完成。

| 部分 | 负责 | 边界 |
|---|---|---|
| 前端（Compose、ViewModel） | 输入、导航、编辑位置、加载、空结果、失败和成功反馈 | 页面发出动作并展示状态。ViewModel 调用业务接口，收到持久化成功结果后再显示「已保存」。 |
| 业务接口 | 草稿、完成、查找和媒体等操作的输入、输出与失败行为 | 使用业务 ID、内容和可观察结果。需要持续刷新时使用 Flow。变更接口时同步核对调用方和已有数据。 |
| 本机后端 | Room 查询、提交事务、媒体原件、回收站、迁移 | 集中执行“只检索有效正式记录”等规则。DAO、Entity 和持久文件路径由实现管理；搜索、列表和详情引用同一份记录。 |

**首批接口约定**（名称可随代码约定，行为须一致）：

| 操作 | 输入 → 成功结果 | 失败或边界行为 |
|---|---|---|
| 保存／续写草稿 | 当前文字及编辑位置 → 成功落盘的草稿 ID；按该 ID 重开 → 上次成功保存的内容和位置 | 空编辑退出不新建草稿；写入失败如实提示，可重试。中断恢复以成功落盘的内容为准。 |
| 完成草稿 | 草稿 ID 与最终编辑状态 → 稳定的正式记录 ID | 先确保最后一次输入参与本次提交；正式内容写入与本次草稿移除同属一个 Room 事务。失败保留草稿和已有正式版本，重试成功只产生一份结果。 |
| 搜索正式记录 | 中文关键词 → 记录 ID 和预览，按 ID 打开详情 | 未完成修改仍按上次完成的正文匹配。新建草稿和回收站记录不出现在结果中。读取错误与零条匹配分别反馈。 |

只实现本卡用到的接口和错误处理。优先复用已有组件和查询，把同一条业务规则放在一处。有真实的第二个用途或测得的问题时，再评估抽象、拆模块或优化。

### 创建分支

- 从最新 `origin/main` 为一批能一起验收的改动开一个短期分支。围绕同一条使用流程的多张卡可以在这个分支上陆续完成，按完整子功能组织提交。
- 每完成并验证一个完整子功能后及时 commit。等这批功能达到共同的验收条件，再用一个 PR 提交整组改动。若下一项需要单独发布、单独回退，或另一位开发者需要先合入其中一部分再开工，就在该处拆分。审核中的修正继续推到原分支。
- 分支名用 `前缀/英文短主题`，单词用小写和连字符。功能、修复、文档、产品设计分别可用 `feat/`、`fix/`、`docs/`、`design/`。Codex 创建的分支沿用仓库已有的 `codex/` 前缀，如 `codex/engineering-workflow`。前缀只用于命名，两位开发者都可以领取任一类任务。
- 例如开始做正式记录搜索，先用 `git status --short --branch` 核对当前工作，再运行 `git fetch origin` 和 `git switch --no-track -c feat/search-records origin/main`。工作区有其他未提交的任务时先隔离它们，必要时用独立 worktree。已推送的分支通过追加提交修改，保留协作者正在审核的历史。

### 编写 commit

- 一次 commit 交付一个可以独立验收、审阅和回退的完整子功能，把相关子操作及其接口、存储、迁移、测试和使用说明一起提交。例如图文混排的插入、移动、移除、撤销，以及对应的草稿恢复和正式记录更新，合为一条功能提交。
- 较大的开发批次按几个完整子功能分步提交。例如“删除、立即撤销与回收站恢复”和“永久删除与媒体引用清理”可以各自提交。根据功能范围、依赖和审阅成本确定边界，不按文件、单个方法或固定行数拆分，也不为凑行数或提交数合并无关工作。独立的小范围缺陷修复，以及改变规则、需求、接口或使用说明的实质文档调整，可以单独提交。仅记录“已推送”“已创建 PR”“CI 通过”等流程状态的变化不单独提交，按[文档与进度同步](#文档与进度同步)处理。
- 标题用 `类型: 中文动词短语`，点明这次提交改变了什么。例如 `fix: 恢复草稿后保留最后一次落盘的文字`。常用类型为 `feat`（功能）、`fix`（修复）、`docs`（文档）、`design`（产品设计）、`test`（测试）、`ci`（流水线）。标题说清结果即可收笔。涉及多个行为、接口或旧数据时，空一行在正文写明最终变化和影响。省略试过的方案、调试经过和逐文件修改清单。
- 提交前按文件或代码块暂存，用 `git diff --cached` 从头看一遍；再用 `git diff --cached --check` 检查格式，运行与改动有关的验证。需要提交前审核时，先给出文件范围、拟用标题及正文、已验证结果，确认后再 commit。

### 创建与审核 PR

- 首次推送可用 `git push -u origin HEAD`。创建 PR 前核对来源分支、目标 `main` 和完整文件差异。标题沿用 commit 的写法，概括整组变更。单提交 PR 可直接沿用提交标题。
- 正文通常只需 **变更** 和 **验证**。变更按本 PR 交付的结果归纳，可关联任务卡。例如“搜索只返回有效正式记录，草稿和回收站内容均排除”。多条 commit 共同完成一项行为时，在 PR 中写一次即可。迁移、共享接口或签名交付有变化时，说明使用方需要知道的影响。
- 验证写实际检查的范围、结果及影响验收的未验证项，例如“Room 查询测试通过，覆盖正式记录、草稿和回收站三类数据”。命令或日志仅在有助于复现问题时引用。PR 省略开发尝试和排查经过。
- 另一位开发者从仓库的开放 PR 列表进入审核，无需专门通知或指定审核人。意见留在对应差异行，作者在原分支修正并回复，审核人复核最新改动。
- 审核人核对需求、数据影响和验证结果。审核通过、待修改意见已处理且已配置的相关 CI 通过后，审核人即可直接合入 `main`。尚未配置 CI 时，以 PR 中记录的本地检查作为验证依据。合并后可清理已完成的任务分支。

## 四、联合验收与首轮后续卡

**文字闭环。** 在 Android 10 或以上设备使用空测试库，开启飞行模式，全程无需登录。

1. 从「随手记」输入“青瓦桥初雪”，确认草稿落盘，暂时离开编辑，在「搜索全部记录」查“青瓦桥”，预期 0 条。
2. 强行停止应用，保留应用数据。重新启动，从「记录 → 继续草稿」打开，核对原文和续写位置。
3. 追加“，河边见”并点「完成」。预期回到「随手记」，通过「已保存 · 查看」打开完整正文。
4. 再搜“青瓦桥”，预期 1 条。搜索与保存反馈指向同一记录 ID，草稿入口已移除本次草稿。

**照片。** 拍照／系统选图与原图保存、按顺序预览可分别领卡。先把原件写入应用持久目录并确认可读，再保存草稿引用。联调检验移除相册来源后仍能重新打开原图，保存失败时保留此前成功的内容，拒绝相机权限后仍能写文字。[照片记录](../requirements/A-记录与保存.md#r003-照片记录)

**删除与恢复。** 可先用文字打通删除、立即撤销和回收站，再验“正式旧图＋草稿新图”。删除后两者从普通入口隐藏；回收站只读展示正式内容并提示有草稿；恢复后正式记录可查看、草稿可续写。仍被正式记录、草稿、回收站或可撤销操作引用的原图须保留。[删除恢复规则](../requirements/H-隐私与数据保护.md#删除恢复的共同规则)

首轮出包前，按版本规划补验已有记录的编辑与放弃、文字与照片的插入／移动／移除与撤销、精确或留空的事件时间、自动记录时间和双时间浏览。视觉风格单独评审。[首轮交付范围](../requirements/版本规划与审核事项.md#首版迭代安排已确认)

## 五、构建、验证与 CI

从仓库根目录使用 Wrapper。以下为约定的 Windows 命令；Linux CI 使用 `./gradlew` 和相同的任务名。

| 用途 | 命令／操作 | 通过依据 |
|---|---|---|
| 日常构建与快速测试 | `.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug` | 测试通过，生成可安装的调试 APK。 |
| 设备集成测试 | 先启动模拟器或连接测试设备，再执行 `.\gradlew.bat :app:connectedDebugAndroidTest` | 真实 Room 和涉及 Android 平台的关键路径通过。 |
| 每轮交付 | 在受控签名环境执行 `.\gradlew.bat :app:assembleRelease` | 验签并安装该 APK，按本轮范围验收。签名密钥和密码由发布环境提供。 |

**选择测试看风险。** 将断言放在能够捕获错误的最低成本层。查询排除草稿和回收站，用一个真实 Room 用例覆盖；页面只核对打开正确详情和返回位置。验证落盘可关闭并重开数据库；进程被终止后的恢复用候选 APK 实测。普通文案、布局改动做构建和针对性页面检查即可。修复缺陷时优先保留能复现该缺陷的最小回归；事务失败、照片保存中断、旧库迁移等可能造成数据损失的路径值得专测。

**CI 触发与失败处理。** 面向 `main` 的 PR 每次更新都自动构建并执行快速测试；改动涉及数据库、媒体、迁移或跨模块行为时，加跑对应设备测试。每次合入 `main` 后再次构建并执行核心集成回归。保留测试报告、失败任务日志和调试 APK。PR 作者查看首个失败任务，用同一命令复现、修复并推送复测；`main` 失败时由最近合入相关改动的作者牵头，恢复通过后再交付。

**两项按需验证的实践：**

- **变异测试**用于检查现有测试的辨错能力。例如临时变异查询谓词，使回收站记录混入结果，再运行既有查询测试。若变异存活，先确认它确实改变产品行为，再用一个针对性样本补缺口。适合在关键规则稳定后局部运行，不设全仓分数门槛。
- **形式化验证**用于难以靠几个例子审清的状态组合。若照片引用清理变得复杂，可将替换、放弃、完成、删除、恢复和清理建成有限状态模型，用模型检查器搜索违反“有有效引用的原图仍存在”的操作序列。记录模型边界，发现反例后用该序列检查实现。实际文件读写仍在设备上验证。

## 六、每轮 APK 交付

从已验收的 `main` 提交生成签名 APK，附提交号、版本、变更说明、实测设备与结果、未验证项。首个可用版本验证全新安装；有上一版时，用相同应用 ID、相同签名和更高版本号覆盖安装，核对旧记录、草稿及媒体，涉及数据库变更时验证对应迁移。每轮按新增能力覆盖离线、无 Google Play 服务、相关权限被拒和恢复路径。[设备兼容与交付](../requirements/版本规划与审核事项.md#设备兼容与交付已确认)
